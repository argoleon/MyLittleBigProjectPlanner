# Database migrations

Versioned SQLx migrations, applied in order and only once:

- by the `api` at startup when `DATABASE_MIGRATION_URL` is set;
- or by `api migrate` (locally: `just migrate`), for deployments that run migrations as a separate job.

Never edit a migration that has been merged: add a new one. Name files `YYYYMMDDHHMMSS_short_description.sql`.

## Roles

Created by the deployment (`deploy/postgres/init-roles.sh` in Docker Compose), never by migrations:

| Role | Used for | Rights |
| --- | --- | --- |
| `mlbpp_owner` | migrations | owns the schema and every table |
| `mlbpp_app` | `api`, `worker`, at runtime | only the grants given below; neither owner nor `BYPASSRLS`, so it cannot disable row-level security |

## Business table checklist

Every table holding tenant data follows these conventions (specification §18):

```sql
CREATE TABLE widget (
    id         uuid PRIMARY KEY,                       -- UUID v7, generated by the application
    tenant_id  uuid NOT NULL REFERENCES tenant (id),
    label      jsonb NOT NULL,                         -- translatable: {"fr": …, "en": …}
    due_on     date,                                   -- planning dates: local date, never UTC
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    version    bigint NOT NULL DEFAULT 1               -- optimistic concurrency
);
CREATE INDEX widget_tenant_due_idx ON widget (tenant_id, due_on);  -- indexes start with tenant_id
SELECT app_setup_business_table('widget');
```

`app_setup_business_table` enables and forces row-level security with the `tenant_isolation` policy, grants read and write access to `mlbpp_app`, and maintains `updated_at`.

The `rls_check` integration test fails the build if a table in `public` lacks row-level security, a policy or a `tenant_id` column. Only `tenant` (keyed by its own id) and, later, `account` (global accounts, specification §3) are exempt from `tenant_id`.

## Tenant context

The request layer opens each transaction with `set_config('app.tenant_id', <id>, true)` (the parameterized form of `SET LOCAL`). The setting ends with the transaction, so a pooled connection never carries a tenant to the next request. Outside a tenant context `app_current_tenant()` is `NULL` and no row is visible.
